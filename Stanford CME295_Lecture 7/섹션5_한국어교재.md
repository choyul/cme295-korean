> 원문 출처: Stanford CME295, Autumn 2025, Lecture 7, 타임스탬프 (1:20:38)~(1:32:11)

## 1. 강의 개요

- 도구의 세 가지 범주 — 정보(검색·날씨·주식)·계산(코드 실행)·행동(이메일 전송 등) — 를 다룬다.
- 도구가 많아질 때의 문제(컨텍스트 한계·needle-in-haystack)와, 이를 푸는 도구 선택(tool selection/routing)을 본다.
- 도구 정의·사용을 표준화하는 MCP(Model Context Protocol)를 설명한다.

---

## 2. 학습 목표

1. 도구의 세 범주(정보·계산·행동)를 예와 함께 구분할 수 있다.
2. 도구가 많을 때의 문제와, 도구 선택(routing)이 이를 어떻게 푸는지 안다.
3. MCP가 표준화하는 것(도구 노출 방식)과 구성요소(서버·도구·프롬프트·리소스)를 이해한다.

## 3. 본문

### 블록 1 — 도구의 세 범주

**영문 원문**
> (1:20:38) information (...) you ask your LLM about news of the day (...) an API that fetches it (...) search (...) weather, stocks. (...) (1:21:41) calculation (...) transform the query into code, execute that code and then read out the answer. (...) (1:22:11) take actions on behalf of the user (...) a tool that sends emails (...) hit send for you.

**한국어 번역**
도구의 세 가지 범주:
1. **정보(information)**: 모델이 모르는 정보를 외부에서 가져옴. 예: 오늘 뉴스(검색 도구), 날씨, 주식. (지식 컷오프를 RAG와 다른 방식으로 메움)
2. **계산(computation)**: 추론 사슬로 풀게 둘 수도 있지만, 질의를 코드로 바꿔 실행하고 답을 읽어오는 게 더 확실. 계산 영역에 도구 호출이 두루 쓰임.
3. **행동(actions)**: 사용자를 대신해 행동. 예: 이메일 전송 도구 — 모델이 제목·본문을 채우고 전송까지 함(외부 세계와 상호작용하는 구성요소가 있으므로).

도구 호출은 매우 강력해 사실상 무엇이든 할 수 있습니다.

**용어 설명**
- **정보 도구**: 검색·날씨·주식 등 외부 정보 조회.
- **계산 도구**: 질의를 코드로 실행해 계산.
- **행동 도구**: 이메일 전송 등 실제 행동 수행.

### 블록 2 — 도구가 많을 때의 문제

**영문 원문**
> (1:22:45) you wouldn't have just a single tool API (...) you would have several ones (...) (1:23:46) too many tools (...) some tool API will get lost in the context (...) needle in a haststack (...) (1:25:21) you might end up being mediocre at all of them (...) the context window that is finite (...) you couldn't possibly fit all of such tools.

**한국어 번역**
실제로는 도구가 하나가 아닙니다. LLM은 곰인형 찾기만 하는 게 아니라, 안기·기분 확인·선물 보내기 등 여러 일을 할 수 있어, 무엇이 필요할지 모르니 관련 함수를 다 프리앰블에 넣어 둡니다.

문제: 도구가 너무 많으면 —
- needle-in-haystack 문제처럼, 어떤 도구 API가 긴 컨텍스트에 묻혀 무엇을 써야 할지 모르게 됩니다(API들이 충돌하기도).
- 모든 경우를 지원하려다 모든 것에 어중간(mediocre)해질 수 있습니다.
- 컨텍스트 창이 유한해, 수억 사용자의 모든 도구를 한 번에 다 담을 수 없습니다.
- 또 도구 정의 방식이 LLM마다 제각각이라 표준화가 필요합니다.

**용어 설명**
- **도구 과다 문제**: 도구가 많으면 컨텍스트에 묻히고 충돌·어중간·용량 한계가 생김.

### 블록 3 — 도구 선택 (tool selection / routing)

**영문 원문**
> (1:26:26) a tool selector system (...) two steps (...) a list of tools (...) only contains the API name and (...) one or two words about what it does (...) ask the LLM to pick the tools that might be relevant (...) a tool selector (...) router. (...) (1:27:27) take all the selected tool APIs and feed only those to the context.

**한국어 번역**
도구 사용을 확장 가능하게 하려면 도구 선택(tool selection)을 합니다(구글 딥마인드 기술 논문). 두 단계:
1. 질의와 함께, (이름·한두 단어 설명만 담은) 큰 도구 목록을 LLM에 주고 "관련 있을 만한 도구를 골라라"고 합니다. 이 시스템을 도구 선택기(tool selector), 또는 라우터(router)라 합니다.
2. 고른 도구들의 전체 API만 컨텍스트에 넣어 질의와 함께 처리합니다.

이렇게 도구 수를 쓸 만한 것으로 제한합니다. (RAG로 구현할 수도 있지만 꼭 그럴 필요는 없음)

**용어 설명**
- **도구 선택/라우팅(tool selection/routing)**: 많은 도구 중 관련된 것만 골라 컨텍스트에 넣는 것.
- **도구 선택기/라우터(tool selector/router)**: 관련 도구를 고르는 시스템.

### 블록 4 — MCP (Model Context Protocol)

**영문 원문**
> (1:29:02) every tools implementation (...) can be bespoke to a given LLM (...) duplication (...) (1:29:33) MCP (...) from the anthropic team (...) standardizes the way tools are exposed to models (...) the model context protocol. (...) (1:30:06) an MCP server which is the instance that serves tools (...) tools (...) prompts (...) resources (...) MCP clients.

**한국어 번역**
도구 구현 방식이 LLM마다 제각각이면 같은 도구를 LLM마다 다시 구현해야 해 중복이 생깁니다. 그래서 표준 MCP(Model Context Protocol, 모델 컨텍스트 프로토콜)가 나왔습니다(Anthropic). 도구를 모델에 노출하는 방식을 표준화하는 프로토콜입니다. 핵심 용어:
- **MCP 서버(server)**: 도구를 제공하는 인스턴스.
- **도구(tools)**: 사용자가 쓰게 할 함수 구현.
- **프롬프트(prompts)**: 도구 사용법을 보여주는 템플릿.
- **리소스(resources)**: 과제 수행에 쓰는 외부 DB 등.
- **MCP 클라이언트(clients)**: LLM 호스트 쪽에서 서버와 1:1로 연결되는 부분.

예: 곰인형이 시를 좋아해 시집을 추천하려면 — LLM 호스트(예: Claude), 책 제공자가 구현한 MCP 서버(책 찾기·추천 도구), 사용법 프롬프트, 리소스(곰인형의 소장 목록·베스트셀러)로 구성할 수 있습니다.

**용어 설명**
- **MCP(Model Context Protocol)**: 도구 노출 방식을 표준화한 프로토콜(Anthropic).
- **MCP 서버/클라이언트**: 도구 제공 인스턴스 / LLM 호스트 쪽 연결부.
- **tools/prompts/resources**: 도구 / 사용법 템플릿 / 외부 자원.

## 부록. 실무 적용 포인트 (NLP·LLM 기술 내용 한정)

- **도구의 세 범주는 "AI로 무엇을 자동화할 수 있나"의 지도다.** 정보 조회(실시간 통계·날씨), 계산(보조금 산정 코드 실행), 행동(공문 발송·일정 등록)으로 나눠 보면, 어떤 업무를 도구 호출로 자동화할지 구상하기 쉽다.
- **도구 선택(routing)은 "기능이 많아질수록 골라 쓰는 구조가 필요하다"를 보여준다.** 업무 자동화 도구가 늘면 한 번에 다 넣을 수 없어, 상황에 맞는 것만 고르는 단계가 필요하다. 복잡한 업무 자동화를 설계할 때의 구조적 고려사항이다.
- **MCP는 "도구를 표준 방식으로 한 번 만들어 여러 AI에서 쓰는" 길이다.** 표준 프로토콜 덕에 기관이 만든 도구(내부 시스템 연동 등)를 특정 AI에 종속되지 않고 재사용할 수 있다. 장기적으로 도구를 MCP로 노출하면 도구별 중복 구현을 줄일 수 있다.
