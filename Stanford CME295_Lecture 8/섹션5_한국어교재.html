섹션 5. 에이전트 평가 — 일곱 가지 실패 유형

📄원문 출처: Stanford CME295, Autumn 2025, Lecture 8, 타임스탬프 1:00:14~1:23:26

1. 강의 개요

  • 에이전트(ReAct 루프)를 평가하려면 어디서 실패하는지 알아야 한다. 도구 호출 한 루프(도구 예측→실행→응답 합성)의 실패를 짚는다.
  • 도구 예측 단계의 네 실패(미사용·도구 환각·잘못된 도구·잘못된 인자)와 그 원인·해결을 본다.
  • 도구 실행 단계의 두 실패(잘못된/없는 응답)와 응답 합성 단계의 한 실패, 그리고 공통 교훈을 정리한다.

2. 학습 목표

  1. 에이전트의 한 루프가 도구 예측·실행·합성 세 단계로 나뉨을 안다.
  2. 도구 예측의 네 실패 유형과 각 해결책(라우터·프롬프트·API 개선·모델 업그레이드)을 설명할 수 있다.
  3. 도구 실행·응답 합성의 실패와, "출력은 항상 의미 있게"·"오류를 범주화하라"는 교훈을 이해한다.

3. 본문

한국어 번역

벤치마크에 앞서, 에이전트 평가를 봅니다. 에이전트는 ReAct(관찰·계획·행동) 루프로 여러 원자 단계를 반복합니다(Lecture 7). 한 루프(도구 호출)는 세 단계로 나뉩니다.

  1. 도구 예측: 올바른 도구를 올바른 인자로 고름.
  2. 도구 실행: 그 도구를 실행.
  3. 응답 합성: 도구 호출과 결과를 바탕으로 마지막에 답을 추론.

에이전트 워크플로는 이런 루프를 여러 번 거칩니다. 각 단계에서 무엇이 잘못될 수 있는지(실패 유형)를 알아야 평가 결과를 해석할 수 있습니다.

용어 설명
에이전트 한 루프
도구 예측 → 실행 → 응답 합성. (ReAct, Lecture 7 참고)
실패 유형(failure mode)
각 단계에서 생길 수 있는 오류.

한국어 번역

도구 예측 단계의 네 실패 유형:

  1. 도구 미사용(punt): 도구가 필요한 질의인데 도구를 안 쓰고 "못 하겠다"고 회피(어시스턴트 용어로 'punt'). 원인·해결 둘:
  • 도구 라우터(tool router)가 그 도구를 후보에 안 넣은 재현율(recall) 오류 → 라우터 조정.
  • 라우터엔 있었는데 LLM이 쓸 생각을 못 함 → 도구 사용 학습(SFT) 보강 또는 프롬프트 수정.
  1. 도구 환각(tool hallucination): 정의되지 않은 함수명을 호출(예: 정의된 건 find_teddy_bear인데 find_bear를 호출). 원인·해결:
  • 모델이 너무 약해 근거를 못 잡음 → 모델 업그레이드.
  • API가 모델 입장에서 잘 안 쓰임 → 함수명·인자·설명(이 셋이 모델이 보는 전부)을 다듬어 더 논리적으로.
  • 상위(공통) 지시가 "주어진 함수를 쓰라"고 명확히 안 함 → 상위 지시 점검·개선.
  1. 잘못된 도구 선택: "근처 곰 찾기"에 메시지 보내기 같은 다른 합리적 도구를 씀. 우리가 원하는 동작이 명확하지 않아서. → 라우터 점검 + 두 함수 API의 범위(scope) 충돌 해소(어떤 상황에 어떤 도구인지 정밀하게).
  2. 잘못된 인자: 올바른 도구지만 인자가 틀림(예: 위치를 0,0으로). 원인·해결:
  • 모델이 내 위치를 모름(질의에 안 줌) → 컨텍스트에 위치 정보 보강, 또는 위치 탐색 도구를 먼저 실행(권한 없으면 사용자에게 의미 있는 오류 표시).
  • 모델이 인자에 뭘 넣을지 모름 → 도구 사용 재학습 또는 API 재작성.
용어 설명
punt(미사용 회피)
도구가 필요한데 안 쓰고 답을 회피하는 것.
도구 라우터 재현율 오류
라우터가 필요한 도구를 후보에 안 넣음.
도구 환각(tool hallucination)
없는 함수를 호출.
범위 충돌(scope conflict)
여러 도구의 적용 범위가 겹쳐 혼동.

한국어 번역

도구 실행 단계의 두 실패:

  1. 잘못된 응답: 도구 코드에 버그가 있어 엉뚱한 값·오류를 반환. (위치 권한 없을 때처럼 오류가 유용할 때도 있지만) 보통은 오류를 그대로 반환하지 않는 게 좋습니다 — 모델이 "내부 오류라 못 했다"는 식의 비실행적 답을 내기 쉽기 때문. 해결: 구조화된 출력으로 의미 있게 전달(소프트웨어 버그면 그냥 고침).
  2. 응답 없음: 아무것도 반환하지 않음. 특히 '행동'을 하는 도구(예: 온도 올리기)에서 나쁨 — 성공 여부를 모델이 몰라, "올렸어요"라는 거짓 확인을 줄 수 있음. 해결: 도구 호출 뒤엔 항상 의미 있는 출력을 둠. 예컨대 곰인형을 못 찾았을 때도 None이 아니라 빈 JSON을 반환하는 게 낫습니다 — 빈 JSON은 "못 찾음"이라는 의미를 담지만 None은 아무 의미가 없기 때문.
용어 설명
잘못된 응답
도구 버그로 엉뚱한 값/오류 반환. 의미 있게 전달하도록 수정.
응답 없음
행동 도구에서 특히 위험(거짓 확인 유발). 항상 의미 있는 출력을.
빈 JSON vs None
빈 JSON은 '없음'을 의미하나 None은 무의미 → 빈 JSON이 나음.

한국어 번역

응답 합성 단계의 실패:

  1. 합성 실패: 도구가 올바른 결과(예: 1마일 거리의 곰 'Teddy')를 줬는데도 모델이 "못 찾았다"고 답함. 원인·해결:
  • 모델이 앞선 내용을 참조 못 함(초기 LLM에서 흔했으나 요즘은 드묾) → 모델 업그레이드.
  • 흔한 원인: 도구가 출력을 너무 많이 반환해, 정작 중요한 정보(Teddy)가 무관한 정보의 바다에 묻힘 → 도구가 의미 있는 것만 반환하도록 수정.
  • 출력이 의미 있게 제시되지 않음 → Python 클래스로 속성(이름·거리 등)을 갖춘 객체로 반환해 명확하게.

공통 교훈(실패 유형 요약): 원인은 대개 ① 모델 측(추론·근거 능력), ② 컨텍스트의 관련성, ③ 도구 라우터·API 모델링(SFT·프롬프트·API 설명), ④ 도구 자체의 버그로 나뉩니다. 도구·평가를 다룰 땐 오류를 체계적으로 범주화해 묶어서 처리하는 것이 핵심입니다 — 매 오류를 즉흥적으로 풀면 끝이 없습니다.

용어 설명
합성 실패
올바른 도구 결과를 받고도 답을 잘못 만듦. 출력 과다·비구조화가 원인.
오류 범주화
실패를 유형별로 묶어 체계적으로 해결하는 디버깅 원칙.

부록. 실무 적용 포인트 (NLP·LLM 기술 내용 한정)

💡 현장에서 써먹기
  • 에이전트 실패 유형은 "AI 자동화가 어디서 깨지는지" 점검표다. 도구를 안 쓰거나, 없는 도구를 부르거나, 인자를 틀리거나, 결과를 잘못 해석하는 등 단계별 실패를 알면, 업무 자동화 도입 시 어디를 모니터링·보완할지 미리 설계할 수 있다.
  • "출력은 항상 의미 있게"는 시스템 연동의 핵심 설계 원칙이다. 도구가 아무것도 안 돌려주면 AI가 거짓 성공을 보고할 수 있다. 행정 시스템과 AI를 연동할 때, 성공·실패·없음을 명확히 구조화해 돌려주도록 설계해야 안전하다(특히 '행동'을 하는 기능).
  • "오류를 범주화하라"는 디버깅 원칙은 모든 AI 도입에 통한다. 실패를 그때그때 즉흥 대응하지 말고 유형별로 묶어 체계적으로 다루는 것이, AI 시스템을 안정화하는 실무 방법이다.
